# xlsm2spec — Excelマクロ資産の業務分析と要求仕様化

## 目的

ドキュメントも保守担当者も存在しない、古いExcelマクロ資産（VBA + シート + UserForm + Access等のDB）から以下を明らかにする。

1. **業務分析**: このツールが何の業務を、どういう手順で、誰が、どう扱っているのか
2. **Excel特有の制約の読み解き**: Excel/マクロならではの制約が業務に与えている影響と、その裏にある本質的な業務要件
3. **要求仕様**: 新システム（プログラム）として作り直す際に、どんな機能・データ・画面・帳票・運用が要求されるか

※「コードの説明」ではなく「**業務を要件として再定義**」するのが本スキルの目的である。

## 前提

- 対象: `.xlsm` / `.xlam`（バイナリVBAを含むOpenXML形式）
- 抽出スクリプト: `<スキル>/scripts/extract.py`
- 依存: `openpyxl`, `oletools`（含む `olefile`）, `access_parser`（Access DB解析用。純Python。MDBツール不要）
  - `install.sh` では上記3つを**デフォルトで導入**する
  - 手動導入なら: `pip install openpyxl oletools access_parser`
  - 検証: `python3 -c "import openpyxl, oletools, access_parser"`

## 作業フロー

### Step 1. 対象ファイルの確認
対象 `.xlsm` のパスをユーザーに確認する。出力先（既定: 対象ファイルと同じ場所の `<basename>_業務分析_要求仕様.md`）と、その他情報（部署、担当業務、運用状況、**連携するDBファイルの場所**）を聞ける場合は聞く。DBファイルがあれば後で実スキーマを突き合わせる。

### Step 2. 抽出の実行
```bash
python3 <スキル>/scripts/extract.py <対象.xlsm> -o <作業ディレクトリ>
```
- スキルのパスは `.opencode/skills/xlsm2spec`（プロジェクト）または `~/.config/opencode/skills/xlsm2spec`（グローバル）を確認して解決する。
- 生成物（材料）:

| 成果物 | 内容 |
|---|---|
| `00_workbook_overview.md` | ファイル情報・シート構成・定義名・画像/図形数 |
| `10_sheet_list.md` | シート一覧と役割推定 |
| `20_vba_summary.md` | モジュール/プロシージャ一覧・呼び出し関係・グローバル・DB参照・メッセージ |
| `25_forms.md` | UserFormのコントロール・種別・イベント・プロパティ |
| `30_buttons.md` | シート上のボタン→マクロ→定義モジュール割当 |
| `40_cross_references.md` | VBA↔シート↔DBのクロス参照 |
| `50_db_schema.md` | Access DBのスキーマ検証とVBA参照の突合（`--db` 指定時のみ） |
| `sheets/<n>_<シート名>.md` | シートごとの列・数式・検証・コメント・ボタン |
| `vba/<モジュール>.txt` | VBAモジュールの完全ソース |

- 抽出失敗時: エラー内容を確認し、依存導入をユーザーに提案する。

### Step 3. 成果物の精読（順に）
1. `10_sheet_list.md` で全体像 → `00_workbook_overview.md`
2. `30_buttons.md` で**操作の起点**（ボタン→マクロ）を掴む
3. `20_vba_summary.md` のプロシージャ一覧・呼び出し関係で処理フローを掴む
4. `25_forms.md` で入力画面を掴む
5. `sheets/*.md` で各シートの列定義・検証・コメントを確認
6. `40_cross_references.md` でデータの流れを確認
7. 必要に応じて `vba/*.txt` の完全ソースを読み、ロジックの詳細を確認する

**重要な読み方**: 抽出成果物は「材料」。そこから業務を**再構成**するのがAIの仕事である。単に抽出結果を羅列してはならない。

## Step 4. 業務分析のノウハウ

### 4.1 業務フローの再構成
- **メニュー→各業務のボタン→マクロ→シート/DB**の対応を一つのフロー表にする（誰が・いつ・何をする）。
- ボタンに書かれた操作名（作成/依頼/受付/入庫/削除/印刷…）がそのまま業務工程名になることが多い。
- 「戻る」ボタンや遷移元フラグ（例: `T1`セル）から**画面遷移図**を再構成する。
- 同一マクロが複数ボタンから呼ばれる場合、呼び出し元（T1等）で分岐している→遷移元の選択肢を網羅する。

### 4.2 列マッピング技法（最重要）
VBAの一覧書き込みはほぼ例外なく以下の形をしている:
```vba
二次元配列(w行, 0) = w行 + 1      'NO（連番）
二次元配列(w行, 1) = ![コード]     '← シートA列から見て列1
二次元配列(w行, 2) = ![品名]      '← 列2
...
Range("A3:O3") = 二次元配列
```
- **配列インデックス = シート列（0始まり）**。この対応から「DBカラム→シート列」の完全マップが復元できる。
- DBからシートへの取り込みプロシージャ（`○○データ取り込み`）と、シートからDBへの書き込みプロシージャ（`○○データセット`）の両方からマップを確認し、**矛盾があれば実DBスキーマで確定**する。
- 空き列（配列で未使用の列）や「内容欄」列（B列のプルダウン選択肢）にも注意: プルダウンセットの選択肢文字列（例: `"入庫,入庫取消,削除"`）は**業務操作の選択肢**そのもの。

### 4.3 状態表現パターン
Excel資産では状態を以下のどれかで表現する。必ず洗い出して状態遷移表にする。
- **NULL列**: 日付/担当者カラムがNULL = 未処理（例: 受付日IS NULL = 未受付、入庫者IS NULL = 未入庫）
- **セル文字列**: 一覧シートの「内容欄」に操作名を選択（例: 「削除」「出力」「入庫」）
- **フラグセル**: 離れたセルに遷移元や担当者（例: `T1`=戻り先、`N5`=担当者）
- **グローバル変数**: ダブルクリック等で選択データを渡す（`wコード`, `w管理NO`…）
- **表示文字列**: 取り込み時に「入庫済み」等の文字列を固定列に書き込む

NULL表現は「欠番・状態異常」を生みやすいため、新システムでは明示的なステータス列＋状態遷移管理へ置き換える（制約C2参照）。

### 4.4 業務ルールの抽出
以下に注目して「業務ルール一覧」を作る。
- 入力チェック（例: 数量が数値かつ**最小発注数量以上**、コード重複禁止、必須項目）
- 採番方式（接頭辞＋桁数、例: `"H" & Format(n, "0000000000")`）
- 整合性チェック（例: 分割数量の**合計＝元数量**）
- 状態遷移の条件（例: 「入庫取消」は入庫済み行のみ有効）
- 日付・範囲制約（例: 納期は今日±300日、選択肢のComboBox化）
- 正規化（例: コードを大文字・半角に変換して重複防止）
- 集計・換算ロジック（例: 金額 = 数量/基本数量×単価）

### 4.5 エラー・メッセージの読み方
`MsgBox "..."` の文言を一覧化する（`20_vba_summary.md` にメッセージ集計がある場合はそれを利用）。メッセージから**運用上の落とし穴と業務ルール**が見える（例: 「発注数量 < 最小発注数量です」「手配数量 ≠ 分割数量合計」「内容欄に削除が入力されています」）。

### 4.6 デッドコード・休眠機能の検出（重要）
実装はあるが現状使われていない機能を特定し、レポートで明示する。パターン:
- **コメントアウト**: イベントハンドラ（`Worksheet_BeforeDoubleClick` 等）がコメントアウトされ、画面を開く手段が無い
- **実在しないシート参照**: `Sheets("◯◯")` がワークブックに存在しない → 実行時エラー or 未完成機能
- **実在しないカラム参照**: `![注番]` 等が実DBに無い → デッドコードの決定的証拠
- **VBAから未参照のテーブル/クエリ**: DBにテーブル・クエリが存在するのにどのコードからも使われない → 過去の機能・将来計画の名残
- **存在しない画面遷移**: 画面（UserForm）はあるが、起動するコードが無い

「どのコードからも呼ばれない」は `grep` で確認できる。デッドコードは「**設計意図の記録**」として要件の要否確認に使う（例: 分割納期管理、製造計画連動の使用量管理）。

### 4.7 イベント駆動の見落とし防止
- ボタン（OnAction）だけでなく、**ダブルクリック**（`Worksheet_BeforeDoubleClick`、対象列・行の条件に注意）も操作起点。
- `Auto_Open` / `Workbook_Open` 等の起動時処理、`_Change` / `_Activate` 等の画面イベントも業務ルールを含む（例: 起動時に担当者セルをクリア）。
- 条件 `If w行 > 2 And w列 = 2` は「データ行かつB列（コード）」＝その列をダブルクリックすると詳細画面が開く、という**UI規約**。

## Step 5. Excel特有の制約の読み解き（汎用パターンカタログ）

「なぜExcelでこんな作りになっているのか」を解釈し、新システムでどう扱うかを整理する。以下は既存資産で繰り返し現れる代表パターン。**該当するものすべてを洗い出して適用**し、独自パターンがあれば追加する。

| ID | 現状の作り（Excel的実装） | 本質的な業務要件 | 新システムでの扱い |
|---|---|---|---|
| C1 | 一覧＝列定義＋フラットな行データ＋オートフィルタ。DBに整合性制約なし（重複コード・Null混在が防げない） | 一覧の検索・絞り込み・並べ替え。マスタは一意 | テーブル定義＋一意制約/NotNull制約。グリッドUIで検索・ソートを標準化 |
| C2 | 状態を日付/担当者の**NULL**で表現（未受付/未入庫など） | オーダー/伝票に「状態」があり、誰が・いつ確定したかの記録が必要 | 明示的なステータス列＋状態遷移管理＋確定者/確定日時の保持 |
| C3 | 削除は行選択→**物理削除**（DELETE文） | 「削除」は業務操作だが誤操作の取り消しがない | 論理削除（削除フラグ）＋削除前確認＋操作ログ。物理削除は原則禁止 |
| C4 | 入力はUserForm、一覧行はプルダウン選択で操作 | 入力と一覧操作の両方が必要 | フォーム（入力）とグリッド（一覧）の分離。直接編集は権限と項目単位で制御 |
| C5 | 画面遷移・選択を**セルフラグ/グローバル変数**で保持（T1=戻り先、N5=担当者、wコード等） | 前画面・操作者・選択データの保持が必要 | セッション/画面状態（戻る履歴・ログインユーザー・選択コンテキスト） |
| C6 | 処理中に `ScreenUpdating=False` / `DisplayAlerts=False` で画面を固定 | 誤操作防止と画面の安定 | モーダル確認・処理中表示・ロール別画面制御を標準化 |
| C7 | 一覧クリアは `Range("A3:AZ500000").Delete`、最終行判定は `Cells(500000,列).End(xlUp)`（**50万行級の一括操作**） | 表示領域の管理 | DB問合せベースのページング表示。全件一括は不要 |
| C8 | 帳票はExcelレイアウト＋印刷プレビュー（PrintPreview/PrintOut） | 固定帳票（見出し・ヘッダー行・印刷範囲・タイトル行）が必要 | 帳票定義（項目・レイアウト・印刷条件）として要件化。PDF/印刷出力へ |
| C9 | DBはDAO等で都度 OPEN/CLOSE、SQLは文字列連結（注入・型崩れリスク） | データアクセス層の分離と安全なクエリ | リポジトリ層・パラメータ化クエリ・接続プール |
| C10 | 表示は「二次元配列→Range 一括代入」（`Range("A3:R"&n)=配列`） | 一覧データの高速描画 | グリッドのデータソース化（サーバーサイド成形） |
| C11 | **実績登録しても在庫/残高等が自動更新されない**（月次で一括補正する運用） | 在庫等の管理はあるが**手動/定期補正** | 登録時のリアルタイム更新（トランザクション）。定期締めは「期首残」の別概念へ |
| C12 | 警告（安全在庫以下・在庫0）を**文字列セル**で表示 | 補充判断のための警告 | アラート一覧/ダッシュボード。マスタ属性から**自動発注提案**まで拡張可能 |
| C13 | 採番は採番テーブルを Read→+1→Write（**排他なし**） | 連番による一意な識別子 | DBの自動採番（シーケンス/AUTO_INCREMENT）で欠番・競合を排除 |
| C14 | シート保護（**パスワード無し** Protect/Unprotect）で入力規制 | 入力可能列の制限 | ロール/権限による入力制御 |
| C15 | VBAが**実在しないシート/カラムを参照**している | 未実装・未完成の設計意図（詳細画面、属性追加等） | 参照を要件に含めるか要否確認 |
| C16 | **デッドコード**（起動手段が無い画面、コメントアウトされた機能） | 過去にあった業務（分割納期管理など）の名残 | 機能要否をヒアリング。必要なら再実装 |
| C17 | 入力の選択肢を**別シートの表示範囲**（RowSource）に依存 | 選択肢データがマスタと同期している必要 | DB/マスタから直接選択 |
| C18 | 実績登録時に**在庫・残数・上限と整合チェックしない**（在庫超過・負在庫が可能） | 業務上の整合確認が必要 | 登録時の在庫チェック（残数・安全在庫・上限の警告/ブロック） |
| C19 | DBに**VBA未参照のテーブル/クエリ**（集計・使用量・統計など）が存在 | 休眠中の機能（計画連動・集計分析）の設計意図 | 用途をヒアリング。不要なら新DBへ移行しない |
| C20 | テーブル定義と**VBAの参照カラムが不一致**（書き込み対象カラムが実DBに無い） | 属性追加の設計意図が定義に未反映 | 属性の取扱いを要件で確定（カラム追加 or 機能廃止） |
| C21 | **空きシート・空き列・未使用の定義名**（承認欄・見出しのみの帳票シートなど） | 帳票レイアウト・承認フローの一部 | 帳票/承認フロー要件として確認 |
| C22 | 印刷物に**記名・承認欄**（作成/審査/承認）がある | 帳票の承認フロー | ワークフロー要件（承認ステップ）の要否を確認 |
| C23 | 集計は**クエリ（Access）やシート計算**で実施し、結果を一覧化（当月入庫数・当月出庫数など） | 期間集計・月次締めの要件 | 集計ロジックをDBビュー/サービスとして実装。集計期間（当月等）の定義を確定 |

## Step 6. DB実スキーマの検証（ある場合）

DBファイル（`.accdb`等）が提供されたら、抽出時点で実スキーマの検証レポートを生成する。

```bash
python3 <スキル>/scripts/extract.py <対象.xlsm> -o <作業ディレクトリ> --db data.accdb
```

- `50_db_schema.md` に以下が自動出力される: テーブル定義（カラム・型・非NULL数・サンプル値）、クエリ一覧（MSysObjects Type=5）、**VBA参照（T_/Q_テーブル名・`![カラム]`・SELECT列）との突き合わせ**、VBA未参照の休眠テーブル検出（C19）、実DBに無いカラムの指摘（C15/C20）
- `access_parser` 未導入の場合は `pip install access_parser` を促す

検証手順（レポートを読み、以下を確認する）:
1. テーブル一覧 → VBAから参照されるテーブルとの対応を確認。**VBA未参照のテーブル**は休眠機能の証拠（C19）
2. カラム一覧 → VBAが `![カラム]` で参照・書き込みする名前の**存在を全て確認**。無いものはC15/C20（未完成・デッドコード）
3. 行数・サンプル値 → 実運用データの有無、コード体系、マスタの状態
4. クエリ一覧 → 集計・結合の構造を推定。SQL本文は抽出不可なことが多いため、**VBAの参照フィールドから再構成**し「推定」と明記
5. **0件のテンプレートDB**である場合は「初期状態のテンプレート」と明記し、実運用DBのスキーマ確認を促す

手動でスキーマだけを確認したい場合は、既存のワンライナーを使う（`--db` の代替）:
```python
python3 -c "
from access_parser import AccessParser
db = AccessParser('data.accdb')
for t in db.catalog:
    if t.startswith('MSys') or t.startswith('f_'): continue
    print('TABLE:', t)
    try:
        tbl = db.parse_table(t)
        print('  COLUMNS:', list(tbl.keys()))
        rows = list(tbl.values())
        print('  ROW COUNT:', len(rows[0]) if rows else 0)
    except Exception as e:
        print('  ERR:', e)
"
```

## Step 7. 要求仕様の導出

新システムの要求仕様を以下に整理する。

- **機能要件**: 一覧・登録・更新・削除・検索・並び替え・帳票出力・状態遷移。既存動作をそのまま「機能」に落とす（**業務は変えず、技術を変える**）。各機能にIDを付与し、業務ルール・制約（R番号/C番号）を紐付ける
- **非機能要件**: 同時利用者、レスポンス、権限（ロール）、監査（登録者/登録日等が既にあれば踏襲）、バックアップ、データ保持期間、移行要件
- **データモデル**: エンティティ・属性・型・必須・既定値・キー。**状態列を明示**。デッドコード/休眠機能のテーブルは要否確認後に移行判断
- **画面設計**: 一覧・入力・確認画面の項目構成（抽出結果を利用）
- **帳票設計**: 帳票ごとに項目・レイアウト・印刷条件・承認欄（C22）
- **権限・監査**: 操作者特定＋全操作ログ。削除は論理削除＋操作記録
- **移行要件**: データ移行、採番値の引き継ぎ、状態の復元方法

## Step 8. 成果物の作成

以下を満たす日本語Markdownレポートを書く。

- ファイル名: `<basename>_業務分析_要求仕様.md`（対象ファイルと同じディレクトリ）
- 根拠は抽出成果物のファイル名で示す（例: `20_vba_summary.md` の `手配管理NO採番`）
- 推測である箇所は「（推定）」と明示し、確証がある箇所と分ける
- 抽出では判明しない事項（利用者数、運用頻度、休眠機能の要否等）は「要確認」リストとして残す
- 本スキルの重要なアウトプットは「制約表（Step5）＋要件」の対応関係。制約を要件へ翻訳した経緯が分かるようにする

## レポート構成（雛形）

## 補足・注意

- 抽出成果物を書き換えない。レポートは別ファイルに書く。
- 日本語の手続き名・変数名・シート名はそのまま引用して良い。
- 大量のプロシージャがある場合は、処理の要となるもの（データ書込、状態変更、採番）を優先して精読する。
- 完全な正確性が難しい箇所は「推定」と明記し、誤った断定を避ける。
- 分析は「業務を要件として再定義」すること。コードの翻訳に終始しない。
